A CPU fundamentally works with machine instructions.

Writing everything directly at the machine-instruction level would be extremely difficult.

Imagine telling the CPU:

Load this register
Move this value
Compare these bits
Jump to this address
Store this result

Programming languages allow us to express the same computational ideas at a much higher abstraction level.

More abstraction
       ↓
Easier development
       ↓
Less direct control

Less abstraction
       ↓
More control
       ↓
More complexity

Learning a language means learning its computational model, not just its syntax.

7. IR / BYTECODE / OTHER REPRESENTATION: At this point the code is transformed into some intermediate representation.
After understanding your program, a compiler/runtime may transform it into another representation.

This is commonly called:

Intermediate Representation (IR)

it provides a useful layer between:

human-oriented source

and: 

CPU-specific machine code

Why Not Directly Source → Machine Code?

You could conceptually design a compiler that goes directly from source to machine code.

But intermediate representations make compiler design much more powerful.

9. MACHINE CODE 

Eventually, for native execution, instructions need to be translated into something the CPU can execute.

For example, conceptually:

LOAD
ADD
STORE
JUMP
COMPARE

At the hardware level, these correspond to machine instructions encoded in binary.

The CPU doesn't execute:

int z = x + y;

It executes instructions appropriate to its architecture.

11. CPU
CPU Architecture Matters

Suppose your computer uses:

x86-64

Another device might use:

ARM64

The machine instructions differ.

That's one reason native binaries are architecture-specific.

Conceptually:

Same source
     │
     ├──────────────→ x86-64 machine code
     │
     └──────────────→ ARM64 machine code

This becomes particularly important when we study Go and native compilation.
